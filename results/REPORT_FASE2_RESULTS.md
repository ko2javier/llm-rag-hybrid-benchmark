**Repo:** `ko2javier/llm-rag-hybrid-benchmark`
**Run date:** 31 July 2026 (§1-11), 01 August 2026 (§12-14)
**Instance:** Vast.ai, 1× RTX 6000 Ada Generation (48 GB VRAM), CUDA 13.2, driver 595.58.03
**Real instance GPU cost:** $0.6966/h (`dph_total`, queried via the Vast.ai API — not `evaluator.py`'s default reference value)
**Reference document:** `FASE2_LEY.md`

*(This is an English translation of `INFORME_FASE2_RESULTADOS.md`, which remains the primary/authoritative version. Same content, same numbers.)*

---

## 1. Executive summary

A full RAG pipeline (bge-m3 embeddings + pgvector HNSW + vLLM) was deployed and evaluated on the synthetic NexusPay dataset (25 Markdown documents, 572 chunks, 50 golden questions: 25 deterministic + 25 semantic) to compare three mid-sized self-hosted models — **Gemma 3 27B AWQ**, **Qwen 2.5 32B AWQ**, and **Gemma 4 31B AWQ** — on cost, latency, and quality (RAGAS), and to weigh self-hosted cost against reference APIs (GLM-5.2, Kimi K3).

**Main finding:** at low volume (this demo's scenario, 50 one-off queries), self-hosting **does not pay off on pure cost** — this confirms the working hypothesis from `FASE2_LEY.md` section 2. The real break-even point sits around **250,000–2,200,000 queries/month** depending on the model and reference API, far above any portfolio/demo volume. The value of this exercise is the demonstrated ability to deploy, measure, and compare real inference infrastructure — not immediate cost savings.

**Second finding, not anticipated in the original design:** the evaluation pipeline (`evaluator.py`) used **pure semantic RAG for all 50 questions**, including the 25 deterministic ones — the deterministic router (`router.py`, verified 25/25 in an isolated test) **was not wired into** the evaluation run. The RAGAS numbers here are valid as a measure of "Exp A" (pure RAG), but do not represent a hybrid pipeline with the router. See section 7. *(Update: this gap was closed on 01 Aug 2026 — see §12.)*

## 4. Methodology

### 4.1 Dataset and pipeline

- **572 chunks** generated by `chunker.py` (`chunk_paragraph` strategy, within the 481-572 range expected by `FASE2_LEY.md`).
- **bge-m3** embeddings (dim 1024) via `embed_server_batching.py`, ingested into pgvector with an HNSW index (`m=16, ef_construction=64`).
- **50 golden questions**: 25 deterministic (`fact_type`: rate_limit, constraint, error_code, version) + 25 semantic — confirmed by direct count of the JSON, not assumed.
- Retrieval: top-5 chunks by cosine similarity (`TOP_K=5`), no reranking or HyDE (Exp B/C out of scope for this run).

### 4.2 Models evaluated

| Role | Model | Checkpoint | Quantization |
|---|---|---|---|
| Candidate 1 | Gemma 3 27B IT | `gaunernst/gemma-3-27b-it-int4-awq` | AWQ 4-bit (1M+ HF downloads) |
| Candidate 2 | Qwen 2.5 32B Instruct | `Qwen/Qwen2.5-32B-Instruct-AWQ` | AWQ 4-bit (official Qwen) |
| Candidate 3 | Gemma 4 31B IT | `QuantTrio/gemma-4-31B-it-AWQ` | AWQ 4-bit |
| RAGAS judge | Mistral 7B Instruct v0.3 | `mistralai/Mistral-7B-Instruct-v0.3` | bf16, unquantized |

All served with vLLM (`--quantization awq_marlin --dtype bfloat16 --gpu-memory-utilization 0.85 --max-model-len 4096 --max-num-seqs 64`), one model at a time, with a VRAM/disk cleanup protocol between each (kill process, verify `nvidia-smi`, delete weights from `/dev/shm`).

**Judge changed from the original plan:** `FASE2_LEY.md` §7 specified `meta-llama/Llama-3.1-8B-Instruct` as the third-family judge. That checkpoint is gated by Meta and requires manual license acceptance tied to the account — not resolvable with a token alone. It was replaced with **Mistral 7B Instruct v0.3** (ungated, 5.18M downloads, a third family distinct from Gemma/Qwen), a decision made explicitly during the session rather than blocking the phase waiting on manual approval.

### 4.3 Cost

Formulas from `FASE2_LEY.md` §8, using this instance's real GPU price (not the script's reference default):

```
self_hosted_cost_per_query = (latency_s / 3600) × $0.6966/h
api_cost_per_query = (input_tokens × input_price/1M) + (output_tokens × output_price/1M)
```

## 5. Technical incidents and resolutions

Documented because each one has real impact on the final numbers or on reproducibility — part of this exercise's value is showing the real debugging work, not just the final result.

1. **HF token lost when forcing `HF_HOME`.** Downloading weights to `/dev/shm/hf_cache` (the RAM rule for large models) overwrote the instance's default `HF_HOME` (`/workspace/.hf_home`, where the user's login lived), causing unauthenticated downloads. No impact on public repos, but it blocked the gated judge's download. Fix: pass an explicit `HF_TOKEN` alongside `HF_HOME` when invoking `hf download`.
2. **Gated judge checkpoint.** See §4.2 — resolved by switching models, not by forcing access.
3. **Mistral repo with duplicated weights.** `mistralai/Mistral-7B-Instruct-v0.3` publishes both the standard HF format (3 `.safetensors` shards, the one vLLM uses) and `consolidated.safetensors` (the `mistral-inference` library's own format, unused here) — doubling the downloaded size (28 GB instead of 14 GB), which matters because `/dev/shm` only has 31 GB. The redundant file was deleted after download.
4. **`ragas==0.4.3` incompatible with `langchain-community==0.4.2`.** Both are pip "latest", but `ragas` imports `ChatVertexAI`/`VertexAI` from a submodule that `langchain-community` removed in its sunset line (moved to a separate package). Top-level, non-lazy import → broke `ragas_eval.py` before running a single row. `ragas/llms/base.py` was patched with a `try/except ImportError` and dummy classes, since those classes are only used in an `isinstance()` check irrelevant to our case (we use `ChatOpenAI` against a local vLLM).
5. **`OpenAIEmbeddings` (langchain) sent pre-tokenized tokens, not text.** By default, `langchain_openai.OpenAIEmbeddings` uses `tiktoken` to chunk the input into integer IDs before sending it (mimicking the real OpenAI API's exact behavior). Our `embed_server_batching.py` only accepts `str`/`list[str]` — every `context_precision`/`context_recall` call failed with a 422. Fixed by adding `tiktoken_enabled=False` to the `OpenAIEmbeddings` instantiation in `ragas_eval.py` (patched in both the working copy and the originally uploaded repo).
6. **Isolated JSON parsing failures from the judge.** With a 7B judge, `ragas` reported a handful of `OutputParserException`s from truncated/malformed JSON in `faithfulness`/`context_recall`. These don't block the run — `ragas` produces `NaN` for that one row and continues. Impact: 1-2 of 50 rows without a valid value for `faithfulness`/`context_recall` on Gemma 3 27B and Gemma 4 31B (see §6.2, `n_valid` column).
7. **Router not wired into the evaluation** (see §7) — not a bug introduced in this run but a design limitation of `evaluator.py`, confirmed by reading the full source (no `import router`, no reference to `api_facts`).

## 6. Results

### 6.1 Self-hosted latency, tokens, and cost (50/50 questions, 0 inference failures across all three models)

| Model | Mean latency | Prompt tokens (mean) | Completion tokens (mean) | Cost/query | Total cost (50q) |
|---|---|---|---|---|---|
| Gemma 3 27B AWQ | 1.30 s | 412.1 | 52.4 | $0.000252 | $0.01259 |
| Qwen 2.5 32B AWQ | 1.37 s | 394.1 | 54.3 | $0.000266 | $0.01328 |
| **Gemma 4 31B AWQ** | **1.01 s** | 416.1 | 35.0 | **$0.000196** | **$0.00978** |

Gemma 4 31B is the fastest and cheapest of the three — also the one generating the fewest output tokens on average (35 vs ~53), which explains most of the cost/latency gap (fewer tokens to generate = less GPU time).

### 6.2 Quality (RAGAS) — aggregate, 50 mixed questions

| Metric | Gemma 3 27B | Qwen 32B | Gemma 4 31B |
|---|---|---|---|
| Faithfulness | 0.874 (49/50 valid) | **0.936** | 0.888 (49/50 valid) |
| Answer relevancy | 0.856 | 0.836 | **0.879** |
| Context precision | 0.959 | **0.968** | 0.961 |
| Context recall | **0.924** | 0.883 | 0.895 |

### 6.3 Quality by question type (key data point — the aggregate hides this difference)

`ragas_eval.py`'s output CSV doesn't keep the original dataset's `type` column (it only copies `question/answer/contexts/ground_truth`); it was recovered by matching question text against `evaluator.py`'s CSV (**exact 50/50 match across all three models, no unmatched questions**).

**Deterministic (n=25):**

| Metric | Gemma 3 27B | Qwen 32B | Gemma 4 31B |
|---|---|---|---|
| Faithfulness | 0.853 | 0.927 | **0.940** |
| Answer relevancy | 0.874 | 0.932 | **0.960** |
| Context precision | 0.944 | **0.961** | 0.944 |
| Context recall | **0.993** | 0.968 | 0.990 |

**Semantic (n=25):**

| Metric | Gemma 3 27B | Qwen 32B | Gemma 4 31B |
|---|---|---|---|
| Faithfulness | 0.895 | **0.946** | 0.833 |
| Answer relevancy | 0.837 | 0.740 | 0.798 |
| Context precision | 0.959 | 0.976 | **0.978** |
| Context recall | **0.855** | 0.798 | 0.797 |

**Reading:**

- **Gemma 4 31B** is clearly superior on deterministic questions (highest faithfulness/answer_relevancy of the three), but degrades the most on semantic ones (faithfulness drops to 0.833, the lowest of the three). The fastest/cheapest model doesn't get there for free in narrative quality.
- **Qwen 32B** is the most balanced — best semantic faithfulness (0.946) and solid deterministic performance, at the cost of being the slowest and most expensive of the three.
- **Gemma 3 27B** sits in the middle on almost every metric, without standing out in either category.
- **Consistent pattern across all three models:** `context_recall` is substantially higher on deterministic questions (0.968-0.993) than on semantic ones (0.797-0.855). Since it repeats identically across all three models, this is an effect of **question type and retrieval strategy** (pure semantic RAG retrieves a single fact from an exact passage almost perfectly; it struggles more to synthesize context scattered across multiple documents for narrative questions) — not a problem specific to one model.

## 7. Deterministic router: not applied in this run (important finding)

Verified directly against the code (not assumed): `evaluator.py` and `ragas_eval.py` **contain no reference** to `router.py`, `classify()`, `fact_type`, or `api_facts`. Confirmed with `grep` on both files — zero matches.

`router.py` was tested in isolation (`test_router.py`) against the 25 deterministic questions: **25/25 PASS**, replicating the May result mentioned in `FASE2_LEY.md`. But that test is never invoked inside the real evaluation pipeline — all 50 questions, including the 25 deterministic ones, went through pure semantic retrieval (embed the question → top-5 cosine similarity → prompt to the LLM), exactly like the semantic ones.

This is **not a bug introduced in this session** — it's the documented design: `FASE2_LEY.md` §9 lists "Exp D — deterministic router vs pure RAG" as a **separate, non-blocking** experiment, distinct from the core (Exp A). `evaluator.py`'s own docstring literally says *"RAG evaluation benchmark ... cosine-similarity retrieval"*, with no mention of a router.

**Implication for interpreting this report's numbers:** they are valid as a measure of **Exp A (pure RAG)** across the 50 mixed question types. They do not represent a hybrid pipeline with deterministic lookup. The data in §6.3 suggests the added value of integrating the router (Exp D) would be pushing `context_recall`/`faithfulness` on deterministic questions toward ~1.0, guaranteed by exact lookup in `api_facts` — not rescuing a broken pipeline, since pure RAG already performs reasonably well on those questions (0.85-0.99 depending on metric and model). *(Update: measured directly on 01 Aug 2026 — see §12.)*

## 8. Self-hosted cost vs reference API

### 8.1 Cost per query

| Model | Self-hosted cost/query | vs GLM-5.2 ($1.40/$4.40 per M) | vs Kimi K3 low ($0.30/$3 per M) | vs Kimi K3 high ($3/$15 per M) |
|---|---|---|---|---|
| Gemma 3 27B | $0.000252 | $0.000807 | $0.000281 | $0.002022 |
| Qwen 32B | $0.000266 | $0.000791 | $0.000281 | $0.001997 |
| Gemma 4 31B | $0.000196 | $0.000736 | $0.000230 | $0.001773 |

At this volume and latency, **self-hosted cost per query is already lower than the reference APIs** in every case — but this per-query comparison is misleading if self-hosting means a GPU running permanently (see break-even below). The self-hosted per-query cost assumes 100% of GPU time is spent processing queries, unrealistic in a low-volume scenario with the GPU mostly idle.

### 8.2 Break-even (monthly volume where self-hosting starts to pay off)

Methodology (`FASE2_LEY.md` §8): fixed monthly self-hosted cost (GPU 24/7) = $0.6966/h × 730 h/month = **$508.52/month**, independent of volume. API cost scales linearly with volume. The crossover:

| Model | Break-even vs GLM-5.2 | Break-even vs Kimi K3 (low) | Break-even vs Kimi K3 (high) |
|---|---|---|---|
| Gemma 3 27B | 629,925 q/month (~20,700/day) | 1,811,620 q/month (~59,600/day) | 251,545 q/month (~8,300/day) |
| Qwen 32B | 643,108 q/month (~21,200/day) | 1,808,488 q/month (~59,500/day) | 254,636 q/month (~8,400/day) |
| Gemma 4 31B | 690,550 q/month (~22,700/day) | 2,213,277 q/month (~72,800/day) | 286,832 q/month (~9,400/day) |

Even in the scenario most favorable to self-hosting (expensive API, Kimi K3 high), it takes processing **more than 8,000 queries/day** for a dedicated 24/7 GPU to be worth it over pay-per-use. For a demo/portfolio of dozens or hundreds of one-off queries, self-hosting never pays off on pure cost under this "GPU always on" model.

**Real nuance:** this break-even assumes the GPU runs 24/7 regardless of usage. If the usage pattern allows powering the GPU down between traffic bursts (e.g. on-demand scaling, spot instances, or Vast.ai billed by actual minute of use as in this session), self-hosted cost gets much closer to the marginal per-query cost — under that regime, with volumes of thousands of queries concentrated in short windows, self-hosting can pay off at significantly lower volumes than the table shows. That comparison wasn't measured here (it would require modeling traffic patterns, out of scope for Phase 2) but it's the most important nuance to raise in a follow-up conversation.

## 9. Conclusion

**The working hypothesis from `FASE2_LEY.md` §2 is confirmed**, with the noted nuance: at low, demo/portfolio-scale volume, self-hosting does not pay off on pure cost against the evaluated reference APIs — the break-even sits in the hundreds-of-thousands-to-millions of queries/month range under the always-on-GPU assumption. The real value of this phase, as the document itself anticipated, is demonstrating the ability to deploy, measure, and compare self-hosted inference infrastructure rigorously (AWQ quantization, VRAM-aware boot order, quality evaluation with a third-family judge, reproducible cost metrics) — not immediate cost savings.

On quality, **there is no absolute winner among the three candidates**: Gemma 4 31B dominates on deterministic questions and on cost/latency, but cedes ground on semantic questions to Qwen 32B, which comes out most balanced at the cost of being the slowest. The "right" choice depends on the real distribution of question types expected in production.

The finding about the un-integrated router (§7) matters so these numbers aren't over-interpreted as the ceiling of what this system can achieve on deterministic questions — with Exp D (router + exact lookup), those figures should approach 1.0 on `context_recall`/`faithfulness` for that subset.

## 12. Exp D — Integrated deterministic router (01 Aug 2026)

**Instance:** a new Vast.ai instance, same reference GPU (RTX 6000 Ada 48GB), real cost **$0.7493/h** (€0.65/h at the day's exchange rate). The 572 chunks, `api_facts`, and dataset were regenerated from scratch (same methodology, see §4).

**Code change:** `evaluator.py` gains `--use-router` — before deciding the prompt, it calls `router.classify(question)`; if the type is `deterministic`, it looks up the `api_facts` (Postgres) row of that `fact_type` with the largest keyword overlap against the question, and uses that exact fact as context instead of semantic retrieval. If there's no match, it falls back to normal semantic RAG (the `retrieval_method` column records which path was used, row by row).

**Bug found and fixed before running (validated offline, no GPU spent):** `router.py` had 2 real bugs that `test_router.py` didn't catch because it only compares `fact_type`, not the exact `keywords` — (1) `normalize()` turned "IP-level" into `"iplevel"` (losing the hyphen), breaking the rule that looks for the `"ip"` token; (2) the `constraint` rule's `subject_map` had only one entry for `"refund"`, so the question about the refund creation window resolved to the wrong fact (the "max refunds per payment" one). Both fixed in `router.py`; re-validated 25/25 correct against the `api_facts` seed before running anything on the instance.

**Run against the 25 deterministic questions only** (the router doesn't touch the semantic ones, no point re-running those):

| Model | Retrieval method | Mean latency | Cost/query |
|---|---|---|---|
| Gemma 3 27B | 25/25 `router_lookup` | **0.20s** | **$0.000042** |
| Gemma 4 31B | 25/25 `router_lookup` | 0.33s | $0.000068 |
| Qwen 32B | 25/25 `router_lookup` | 0.43s | $0.000090 |

All 25/25 resolved to a fact via lookup across all three models (0 fallback to semantic RAG) — confirms the router plus the keyword fix cover 100% of the deterministic subset. Latency and cost drop 5-6x versus the semantic baseline in §6.1 (~1.3s), since it skips embedding the question and the similarity search.

**Quality (RAGAS) — deterministic, router vs semantic baseline (§6.3):**

| Metric | Gemma 3 27B (router → base) | Gemma 4 31B (router → base) | Qwen 32B (router → base) |
|---|---|---|---|
| Faithfulness | 0.960 → 0.853 (**+0.107**) | 0.820 → 0.940 (**-0.120**) | 0.852 → 0.927 (**-0.075**) |
| Answer relevancy | 0.472 → 0.874 (**-0.402**) | 0.531 → 0.960 (**-0.429**) | 0.845 → 0.932 (**-0.087**) |
| Context precision | 1.000 → 0.944 (**+0.056**) | 1.000 → 0.944 (**+0.056**) | 1.000 → 0.961 (**+0.039**) |
| Context recall | 1.000 → 0.993 (**+0.007**) | 1.000 → 0.990 (**+0.010**) | 1.000 → 0.968 (**+0.032**) |

**Reading — the §7 hypothesis is only half-confirmed:**

- **Context precision and context recall saturate at 1.000 across all three models**, exactly as §7 anticipated: exact lookup in `api_facts` eliminates any retrieval error on deterministic questions by design.
- **Faithfulness and answer_relevancy do NOT improve uniformly — they actually get worse in 2 of 3 models.** This wasn't anticipated and has two distinct causes, verified by reading the answers row by row:
  1. **Answer relevancy drops sharply across all three models** because fact-based answers are very short and telegraphic ("1000", "10", "v2") instead of the full sentence semantic RAG produced with narrative context. RAGAS measures relevancy by generating synthetic questions from the answer and comparing them to the original question — a one-word answer gives that metric much less signal, even when it's correct. It's a format artifact, not a content error.
  2. **Faithfulness drops for Gemma 4 31B (-0.12) and Qwen 32B (-0.075)** for a real reason, not an artifact: on several questions (Q007, Q009, Q014, Q018, Q021, Q022, Q024 for Gemma 4; Q007 and Q024 for Qwen) the model answered *"the provided text does not contain information regarding..."* **despite the exact fact being right there in the context**, in compact JSON instead of prose. Gemma 3 27B didn't have this problem (25/25 correct). This suggests the prompt used to present the lookup context (`build_fact_prompt`, raw JSON) is less robust for Gemma 4/Qwen than the semantic RAG's narrative prompt — a prompt-engineering finding, not a router one.

**Exp D conclusion:** the router delivers on its retrieval-side promise (precision/recall at 1.0), but exposes that the *prompt* used to present the exact fact needs work — injecting raw JSON isn't enough, especially for non-Gemma-3 models. This would be the first thing to improve if this line of work continues (see §10).

## 13. Exp B — HyDE on semantic questions (01 Aug 2026)

**Run against the 25 semantic questions only** (HyDE adds nothing on deterministic questions already covered by the router — no point running it there). The same model generates both the hypothetical answer and the final answer (no second model, per the design already documented in §4.2 of the code).

**Cost and latency — HyDE adds one extra LLM call (generates the hypothesis) before retrieving context:**

| Model | Mean total latency (HyDE + answer) | Cost/query |
|---|---|---|
| Gemma 4 31B | **3.05s** | **$0.000635** |
| Qwen 32B | 3.27s | $0.000681 |
| Gemma 3 27B | 3.82s | $0.000796 |

Versus the semantic baseline in §6.1 (~1.0-1.4s), HyDE costs 2.2-3x more per query — consistent with running two generation passes instead of one.

**Quality (RAGAS) — semantic, HyDE vs semantic baseline (§6.3):**

| Metric | Gemma 3 27B (HyDE → base) | Gemma 4 31B (HyDE → base) | Qwen 32B (HyDE → base) |
|---|---|---|---|
| Faithfulness | 0.910 → 0.895 (+0.015) | 0.934 → 0.833 (**+0.101**) | 0.955 → 0.946 (+0.009) |
| Answer relevancy | 0.836 → 0.837 (≈0) | 0.851 → 0.798 (+0.053) | 0.813 → 0.740 (**+0.073**) |
| Context precision | 0.957 → 0.959 (≈0) | 0.970 → 0.978 (-0.008) | 0.985 → 0.976 (+0.009) |
| Context recall | 0.885 → 0.855 (+0.030) | **0.924 → 0.797 (+0.127)** | 0.863 → 0.798 (+0.065) |

**Reading — the §6.3/§9 hypothesis is confirmed even more strongly than expected:**

- **`context_recall` improves across all three models**, exactly as the pattern identified in the original report predicted (pure semantic RAG struggles to synthesize context scattered across multiple documents; HyDE attacks precisely that problem by generating a richer hypothetical answer than the original question before searching).
- **The model that benefits the most is exactly the one that was worst off: Gemma 4 31B**, which had the lowest semantic faithfulness of the three in the baseline (0.833, flagged in §6.3 as its weak point). With HyDE, it rises to 0.934 — the largest faithfulness gain of the three models (+0.101) and the largest recall gain (+0.127). HyDE doesn't just confirm the hypothesis, it specifically fixes the weakness the original report had flagged in this model.
- Qwen 32B and Gemma 3 27B, which already started from decent semantic faithfulness (0.946 and 0.895), improve less in absolute terms — there's less room to gain.
- `context_precision` stays essentially flat across all three — HyDE improves how complete the retrieved context is (recall), not how much noise it carries (precision).

**Exp B conclusion:** HyDE confirms its hypothesis cleanly and without the formatting complication that showed up in Exp D — it consistently improves the identified weak point (recall on semantic questions), and more markedly in the model that needed it most. At the cost of ~2.5x more time/GPU per query, it's a justifiable improvement if semantic/narrative questions are a meaningful share of expected production traffic.
